# What it does

ForensiQ helps a junior digital-forensic investigator understand a computer's event timeline after a security incident. The investigator uploads a CSV of timestamped events (files, USB devices, user activity, browser activity). Python checks and sorts the timeline; a language model then looks for event sequences that may be related and may deserve a closer look (for example: USB connected, confidential file opened, file copied to the USB, USB removed), explains why in plain words, and lists questions to check by hand. It points the investigator at things to examine. It proves nothing and draws no legal conclusion.

# Inputs

One `.csv` file with a header row and these columns (names are case-insensitive):

| Column | Required | Meaning |
|---|---|---|
| `timestamp` | yes | ISO 8601, e.g. `2026-03-14T14:02:11Z` or `2026-03-14 19:32:11+05:30`. No timezone means UTC |
| `event` | yes | What happened, e.g. `USB device connected` |
| `user` | no | Account involved |
| `source` | no | Where the record came from, e.g. `USBSTOR`, `Security Log` |
| `details` | no | Free text: file paths, device names, URLs |

Limits, enforced in `timeline.load_timeline` before any model call: file extension `.csv`; 1 to 200,000 bytes; at most 1,000 events; valid UTF-8, no NUL bytes; every row has a valid timestamp and a non-empty event. Anything else is rejected with exit code 2 and no model call.

**The file is untrusted.** Any cell may contain text written by someone else (a USB volume label, a file name, a URL). It is treated as evidence to analyse, never as instructions. See SECURITY.md.

Where the sample data comes from: synthetic timelines generated by `samples/make_samples.py` (made-up host and user, event types modelled on Windows security log, USBSTOR, filesystem and browser-history records). Public forensic datasets can be converted to this column layout.

# Outputs

The model must return one JSON object that passes the Pydantic model `Analysis` in `schema.py`:

| Field | Type | Rule |
|---|---|---|
| `overall_assessment` | `potentially_significant` or `no_significant_sequence` | |
| `risk_level` | `low`, `medium` or `high` | `no_significant_sequence` must be `low` |
| `significant_events` | list of `{timestamp, description}` | at most 50; empty if `no_significant_sequence`, non-empty otherwise |
| `explanation` | text, 10 to 2000 characters | plain-language reason |
| `forensic_relevance` | text, 10 to 1000 characters | possible relevance |
| `investigator_questions` | list of text, at most 10 | follow-ups to check by hand |

After the schema, `security.check_output` also requires that every cited timestamp exists in the input and that the reply makes no legal conclusion.

`python main.py` prints a report (only when the status is `ok`) and then the status as the last line. The report wraps the model's output with two values computed by Python, not by the model:

```json
{
  "events_analyzed": 51,
  "input_warnings": ["E037 (CSV line 38), field 'details': text that reads like an instruction to an AI was removed before analysis. ..."],
  "analysis": {
    "overall_assessment": "potentially_significant",
    "risk_level": "medium",
    "significant_events": [{"timestamp": "2026-03-14T14:03:58Z", "description": "Q3_Payroll_Master.xlsx was copied to the USB drive (E:)."}],
    "explanation": "...",
    "forensic_relevance": "...",
    "investigator_questions": ["..."]
  }
}
```

Last line and exit code: `ok` 0 (reply passed every check and was used); `invalid_output` 1 (reply failed the schema or the output guard, or was empty); `refused` 1 (the model declined); `error` 1 (no usable reply, the call failed); `rejected` 2 (input rejected before any model call).

# Failure cases

| What goes wrong | What the app does | Last line, exit |
|---|---|---|
| CSV empty, too large, wrong type, bad UTF-8, missing column, bad timestamp, header only | Rejects with a message on stderr; no model call; no `run_log.jsonl` line | `rejected`, 2 |
| `stub:malformed` (JSON that does not parse), `stub:badshape` (parses, wrong shape), `stub:empty` | Reply is discarded, never printed or saved. One retry; each attempt logs `invalid_output` | `invalid_output`, 1 |
| `stub:refused` (or a provider refusal / content filter) | No retry; logs `refused` | `refused`, 1 |
| `stub:error`, `stub:ratelimit`, a network failure | One retry (waits at most 5 s; none for HTTP 400/401/403/404); logs `error` per attempt | `error`, 1 |
| `stub:flaky` (first call fails) | The retry succeeds | `ok`, 0 |
| `stub:fenced`, `stub:preamble` (JSON inside fences or after a sentence) | The JSON object is extracted, then validated as usual | `ok`, 0 |
| Reply cites a timestamp that is not in the input, or states a legal conclusion | Treated as invalid; `guardrail_output` logged | `invalid_output`, 1 |
| A cell contains an instruction-like phrase (`stub:obedient` on `sample_injected.csv`) | The cell is replaced by a placeholder before the model sees it; a warning is shown; `guardrail_input` and `instruction_ignored` logged | `ok`, 0 |

Nothing that failed a check is ever printed to stdout or written to a file other than the two logs.

# Acceptance checks

Each is a command; check the status, exit code and log, never exact wording. Set the stub once, then change the mode:

```bash
export LLM_API_KEY=x LLM_BASE_URL=local://stub
```

| # | Command | Must be true |
|---|---|---|
| 1 | `LLM_MODEL=stub:ok python main.py samples/inputs/sample_ok.csv; echo $?` | last line `ok`, exit 0, one `ok` line in `run_log.jsonl` |
| 2 | `LLM_MODEL=stub:malformed python main.py samples/inputs/sample_ok.csv; echo $?` | `invalid_output`, exit 1, nothing from the reply on stdout |
| 3 | `LLM_MODEL=stub:badshape python main.py samples/inputs/sample_ok.csv; echo $?` | `invalid_output`, exit 1 |
| 4 | `LLM_MODEL=stub:empty python main.py samples/inputs/sample_ok.csv; echo $?` | `invalid_output`, exit 1 |
| 5 | `LLM_MODEL=stub:refused python main.py samples/inputs/sample_ok.csv; echo $?` | `refused`, exit 1 |
| 6 | `LLM_MODEL=stub:error python main.py samples/inputs/sample_ok.csv; echo $?` | `error`, exit 1, no `ok` line in the log |

# Out of scope

From the brief, unchanged: no analysis of disk images, memory dumps, live systems or other raw evidence (CSV timelines only); no automatic response (no deleting, isolating, blocking, or changing evidence; the app only reads the CSV and writes its two logs); no legal conclusions, attribution to a person, or claim that an incident or crime is proven.

Added since the September brief: `user`, `source` and `details` are optional columns (only `timestamp` and `event` are required), because public datasets often lack some of them. The app also reports `input_warnings` (cells it had to neutralise) next to the model's six fields; that value is computed by Python so the model cannot suppress it. Day-first dates such as `14/03/2026` are not supported (see EVAL.md, row 6). Files over 200,000 bytes or 1,000 events are rejected rather than split.
